# Refutation results (independent agents; reproduced on a throwaway local database where stated)

## REQ-13 — confirmed (medium; the insert path is more serious)
Read the latest trg_fn_qc_enforce_review_stages (0126; no later redefinition): Round 1 approval checks only the shape of checker_results (`_qc_results_valid`), never `coa_templates`; the trigger is BEFORE UPDATE only; `qc_insert` checks only the role. On a throwaway database as an authenticated quality_checker: (a) Round 1 approval with invented results for an item with no COA template — allowed; (b) INSERT of a quality_checks row with status 'approved', no reason, no results — allowed; (c) INSERT with status 'checker_approved', no reason — allowed. (b) lets one Quality Checker create an approved record, skipping Round 2 and the two-person rule.

## REQ-14 — confirmed (medium)
Round 2 checks only that Round 1 results exist and that reviewer_results has the same length and shape; not the test/specification text, not that anything changed. `coa_insert` checks only the role; the only coa_records insert trigger checks current approval. As qc_reviewer: approval with reviewer_results naming a different test — allowed. As quality_checker: coa_records insert with made-up result_lines for an approved record — allowed. The "certificate uses reviewer_results ?? checker_results" rule lives only in lib/actions/coa.ts:169-180.

## REQ-06 — confirmed (medium)
packaging_issues has three triggers (pull, transform-and-issue, batch balance) and policies select/insert (roles system_admin, inventory_manager, mfr_manager); no migration up to 0127 checks batch status, and fp_batch_block_reason returns null for any batch that is not approved. On a throwaway database: as inventory_manager, create_packaging_issue on a batch in complete_awaiting_qc — allowed; create_production_issues on a rejected batch — allowed; as mfr_manager, a direct INSERT and create_packaging_issues (R&D) on the rejected batch — allowed. Only the app blocks it (fp_batch_packing_options view; lib/actions/packaging.ts:L174 resolveFpBatch).

## REQ-07 — confirmed (medium)
packaging_issue_items_insert checks only the role; its triggers (unit, stock pull) never look at the parent's voided_at. Reproduced: after voiding PKG-1 (jars 38 → 48), an mfr_manager inserted 7 jars onto the voided PKG-1 — allowed, jars 48 → 41; a second void was refused ("already void"), so the 7 jars are never put back. A header-only INSERT into packaging_issues by inventory_manager was also allowed. The app never writes these tables directly; reachable only through direct API calls by the three write roles.

## REQ-17 — confirmed (medium)
No migration after 0120 touches the Round 2 rules; RLS `qc_update` is the 0001 policy. On a throwaway database, direct UPDATEs by a qc_reviewer moving a record from checker_approved to approved were accepted with: no expiry and no retest period; an expiry 10 days in the past; a 365-day period; a retest approved with a 500-day period. Control: a 180-day period against an expiry 100 days away was refused, so `trg_qc_retest_within_expiry` works but only compares period with expiry. Not enforced by the database: expiry required, expiry not before today, period required, period ≤ 180 days, no period on the final retest.

## REQ-18 — confirmed (medium)
Reproduced: (a) a raw-material retest approved directly with an expiry years later than the batch's earlier approval (2035 against 2027) — accepted; (b) after approval, a same-status UPDATE of retest_period_days (retest date then after the expiry) and of expiry_date — both accepted, because the within-expiry trigger fires only on the move into approved; (c) `load_opening_stock` (only definition 0100), as inventory_manager, accepted an Approved row with retest date after expiry and retests_done = 3. Correction to the analysis: any role with app access can load while opening stock is open. The finished product 180-day / 3-retest / last-retest rules live only in lib/actions/qc.ts. The database does enforce "expired batch not retested" and the within-expiry check at approval.
