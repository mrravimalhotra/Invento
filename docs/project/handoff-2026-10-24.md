## 2. How a change is delivered (unchanged since 18 Oct)

1. Build on the session branch; checks: type-check, lint, `npm test`, build, and `scripts/dev/run-tests.sh` for database changes.
2. A migration ships with the SQL, a suite `supabase/tests/part_*.sql` (registered in the `FILE` map and `ORDER` array of `run-tests.sh`), a line in `expected.txt`, a regenerated `supabase/fresh-install.sql` (`node scripts/build-fresh-install.mjs`), and a line in `docs/modules/` if user-visible.
3. Commit, push the branch, fast-forward `main`. Supabase's GitHub integration applies the migration in about two minutes (wait with a background `sleep 100`, never a foreground sleep).
4. Confirm read-only: `select max(version), count(*) from supabase_migrations.schema_migrations;` plus one query that shows the change itself.
5. Close out: delivery row in `docs/project/deployment-log.md` (Current state, migration register), a pass in `known-issues.md`, the master list (and a new live check `E7x` if Ravi must look), the handoff's migration and pass numbers.

Never run or ask Ravi to run a migration in the SQL Editor. Never write to live data through the connector.

## 8. Traps learned 18 to 20 Oct

- A fresh container has no `node_modules` and Postgres is stopped: run `npm ci` and `service postgresql start` before the checks.
- Supabase's own advisor output is too large for the tool result; summarise it from the saved file with a short script.
- When a migration converts existing rows, the audit trigger logs each change; in the local test database (304 legacy equipment rows) that inflated the audit counts in `des02` and `sb`. Those suites now count only their own test row.
- Trigger functions need no EXECUTE right to fire (checked only when the trigger is created); revoking it is safe.
- Extension functions (pgcrypto) sit in `public` in the local test database but not on live; exclude extension members (`pg_depend deptype 'e'`) in catalog checks.
- `useActionState` returns a new object per submit, but the success text is the same: watch the state object, not `state.success`, in effects.
- The two label sheet previews look alike but must stay separate (pixel-exact to their PDFs).
- Execute SQL runs as the database owner: anything other than SELECT would really change live data.
